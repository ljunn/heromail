# HeroMail 最终产品设计（方案 A）

## 1. 产品定位

HeroMail 是一个可自托管的邮箱资源池与注册验证码平台。平台管理员维护 Outlook/Hotmail 等邮箱资产和各目标平台的收码规则；平台用户不提交自己的邮箱，而是选择目标平台、创建注册任务，由系统分配一个可用邮箱并返回该邮箱收到的验证码。

首版核心不是完整邮件客户端，也不是通用收件箱。核心是：

1. 邮箱资产接入与健康管理。
2. 按目标平台安全分配邮箱。
3. 在租约时间内匹配并提取注册验证码。
4. 记录邮箱在各目标平台的使用情况，避免重复分配失效邮箱。
5. 向网页用户和 API 调用方提供一致的订单状态。

## 2. 关键业务规则

### 2.1 分配单位

分配决策不是只看邮箱本身，而是看 `邮箱 × 目标平台` 的可用性。

- 同一个邮箱可以服务不同目标平台。
- 同一个邮箱在某个平台完成注册后，默认永久标记为该平台已使用。
- 已使用的邮箱仍可在其他未使用的平台被分配。
- 管理员可以手动重置平台占用，但必须写入审计日志。

### 2.2 用户领取流程

```text
用户选择目标平台
  -> 查看价格、库存、预计收码时间和有效期
  -> 创建订单并预扣额度
  -> 系统原子分配一个合格邮箱
  -> 用户复制邮箱到目标平台注册
  -> HeroMail 监听新邮件并按平台规则匹配
  -> 提取并展示验证码
  -> 用户确认完成，或任务超时/取消
  -> 结算订单并更新邮箱的平台占用状态
```

用户不能选择具体邮箱，也看不到邮箱密码、OAuth Token 或完整收件箱。

### 2.3 邮箱筛选条件

候选邮箱必须同时满足：

- 邮箱状态为可用且授权有效。
- 属于该目标平台允许的邮箱池、供应商和地区。
- 没有被其他活跃订单租用。
- `邮箱 × 目标平台` 尚未被使用或封禁。
- 未超过单邮箱日限额、冷却时间和风险阈值。
- 质量分达到平台规则要求。

### 2.4 订单状态

```text
created -> allocating -> assigned -> waiting_code -> code_received -> completed
                    |             |               |                -> disputed
                    |             |               -> expired
                    |             -> canceled
                    -> allocation_failed
```

- `assigned`：已返回邮箱，但用户尚未触发邮件。
- `waiting_code`：用户已点击“我已提交注册”，系统进入高频监听。
- `code_received`：验证码已匹配并展示。
- `completed`：用户确认注册成功，平台占用标记为已使用。
- `expired/canceled`：未收到邮件时，邮箱经冷却后可再次参与该平台分配。
- 只要收到验证码，即使用户随后取消，也默认将该邮箱的平台占用标记为已使用，避免重复注册失败。

### 2.5 计费与退款

- 创建订单时预扣额度，分配失败立即释放。
- 在有效期内未收到匹配邮件，默认自动退款。
- 成功收到验证码即结算；用户是否最终注册成功只用于质量统计，不作为自动退款条件。
- 支持管理员人工补偿、订单申诉和完整资金流水。

## 3. 角色和信息架构

HeroMail 的网页不是登录后才出现的单一管理后台，而是三层连续体验：公开官网、登录后的用户门户、管理员运营后台。三层共享品牌和 API，但路由、信息密度和数据边界明确分开。

```text
公开官网（无需登录）
  首页 / 价格 / API 文档 / 开源部署
        |
        +-- 登录或注册
              |
              +-- 用户门户 /app/*
              |     申请邮箱 / 当前任务 / 订单 / 余额 / 开发者 / 账户
              |
              +-- 管理后台 /admin/*（仅管理员）
                    运行概览 / 资源 / 业务配置 / 订单用户 / 系统
```

### 3.1 公开官网

- 未登录用户可以访问首页、公开价格、API 文档和开源部署说明。
- 价格接口只返回平台代码、名称、描述、允许的邮箱类型、单价和有效期，并且服务端分页。
- 公开接口不返回邮箱库存、邮箱地址、发件人域名、主题关键词、验证码正则、凭证或内部占用状态。
- 首页直接展示“选择平台 -> 分配邮箱 -> 获取验证码”的产品预览；登录后才可创建订单、充值和管理开发者凭证。

### 3.2 平台用户端

导航结构：

```text
工作台
注册服务
  - 申请邮箱
  - 当前任务
  - 订单记录
开发者
  - API 文档
  - API 密钥
账户
  - 用量与账单
  - 余额充值
  - 个人设置
```

核心页面：

- **申请邮箱**：选择目标平台，而不是输入邮箱；展示库存、单价、预计时间、支持邮箱类型和规则提示。
- **当前任务**：突出已分配邮箱、复制按钮、倒计时、等待状态和验证码；提供“我已提交注册”“重新收取”“取消任务”。
- **订单记录**：按平台、状态、时间筛选；展示订单号、分配邮箱、验证码状态、费用、有效期和申诉入口。
- **API 文档/密钥**：以平台代码创建订单，轮询或 Webhook 获取结果。

用户门户使用轻量顶部导航，移动端使用底部四项导航；不能复用管理员侧栏的信息密度。路由统一位于 `/app/*`，刷新或分享深层页面后仍由服务端返回同一个工作台入口。

### 3.3 管理员端

导航结构：

```text
运行概览
资源管理
  - 邮箱资源
  - 邮箱池
  - 接入渠道
业务配置
  - 目标平台
  - 收码规则
  - 调度策略
订单与用户
  - 注册订单
  - 平台用户
  - 余额与流水
系统
  - 告警中心
  - 审计日志
  - 系统设置
```

核心页面：

- **运行概览**：可分配邮箱、活跃租约、今日订单、收码成功率、平均收码时间、收入、异常邮箱和平台库存预警。
- **邮箱资源**：邮箱地址、供应商、授权状态、健康分、活跃租约、已占用平台数、最近收信和操作。
- **目标平台**：平台代码、发件人域名、主题关键词、验证码解析器、允许邮箱池、价格、有效期、库存与启停状态。
- **注册订单**：完整状态时间线、用户、平台、分配邮箱、邮件匹配、费用、失败原因和人工处理。

## 4. 技术架构

沿用此前确定的 Sub2API 式交付方式，但领域模型改为注册任务：

```text
无构建依赖的 HTML + CSS + JavaScript（嵌入 Go 二进制）
            |
        Go / Gin API
            |
  +---------+----------+----------------+
  |                    |                |
分配调度器          邮件 Worker       Webhook Worker
  |                    |                |
Redis 锁/租约/限流   Graph/IMAP 适配器  重试与签名
  |                    |                |
  +---------------- PostgreSQL --------+
```

- 后端：Go、Gin、Ent。
- 前端：无构建依赖的 HTML、CSS、JavaScript；公开官网、用户门户和管理员后台使用独立入口。
- 数据库：PostgreSQL，作为最终事实源。
- Redis：分布式锁、短租约、队列、限流和热点状态。
- Outlook/Hotmail：Microsoft Graph OAuth2 优先，IMAP OAuth2 兼容。
- 部署：前端嵌入单个 Go 二进制；Docker Compose 默认包含 HeroMail、PostgreSQL、Redis。
- 发布：GitHub Releases、GHCR 镜像、一键安装/升级、启动迁移、升级前备份和版本回滚。

## 5. 核心数据模型

```text
users                       平台用户
wallets / wallet_ledgers    余额与资金流水
mailboxes                   邮箱资产和健康状态
mailbox_credentials         加密后的 OAuth 凭证
mailbox_pools               邮箱池与调度策略
mailbox_pool_members        邮箱池成员
target_services             目标平台注册服务
service_rules               发件人、主题、解析器和有效期
service_pool_bindings       目标平台允许使用的邮箱池
mailbox_service_states      邮箱在每个目标平台的可用/占用/封禁状态
registration_orders         注册订单和租约
mail_events                 去重后的邮件事件
verification_results        验证码结果及保留期限
api_keys                    用户 API 凭证
webhook_deliveries          Webhook 投递与重试
audit_logs                  管理审计日志
```

凭证与业务数据分表存储，并使用部署主密钥加密。验证码和邮件元数据设置短保留期，默认不保存完整邮件正文。

## 6. 核心 API

```text
GET    /api/v1/services
GET    /api/v1/services/{code}/availability
POST   /api/v1/orders
GET    /api/v1/orders/{id}
POST   /api/v1/orders/{id}/submitted
POST   /api/v1/orders/{id}/complete
POST   /api/v1/orders/{id}/cancel
POST   /api/v1/orders/{id}/retry
GET    /api/v1/orders
GET    /api/v1/balance
```

创建订单示例：

```json
{
  "service": "github",
  "mail_provider": "auto",
  "request_id": "client-unique-id",
  "webhook_url": "https://client.example/callback"
}
```

成功分配只返回订单所需信息：订单号、邮箱地址、过期时间和当前状态。绝不返回邮箱凭证或其他邮件。

## 7. 首版范围

首版直接支持多用户，因为“用户申请系统邮箱”已经是核心业务，而不是后续功能。

必须完成：

- 用户注册登录、余额/额度、API Key。
- Outlook/Hotmail OAuth2 导入、健康检查和自动刷新。
- 邮箱池、目标平台、收码规则和平台占用记录。
- 网页/API 创建订单、原子分配、轮询收码、订单结算。
- 订单记录、管理监控、基础告警、审计日志。
- Docker Compose、一键安装和版本升级。

暂缓：

- 完整邮件浏览器。
- 用户长期持有邮箱或查看历史收件箱。
- Gmail、QQ、163 等第二批渠道。
- 自动识别未知平台和通用无规则收码。
- 代理商层级、复杂套餐和多币种支付。

## 8. 最终产品原则

1. 用户先选平台，系统再分配邮箱。
2. 邮箱是平台资产，不向用户暴露凭证或收件箱。
3. 调度依据是 `邮箱 × 目标平台`，不是单纯邮箱空闲。
4. 收到验证码即认为该平台使用槽位已消耗。
5. 页面以订单进度为中心，后台以库存质量和平台可用性为中心。
6. 所有状态、资金和人工操作都可审计。
